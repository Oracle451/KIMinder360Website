KIMinder360 Mobile App

Schedule & Milestones

The development of KIMinder360 follows a structured, three-phase implementation plan aligned with the Northern Arizona University Spring 2026 semester, spanning approximately 15 weeks from January 2026 to May 2026. Each phase builds logically on the last — establishing the foundational data layer and core logic first, then expanding into full feature delivery and user interaction, and finally polishing the app for public release. Breaks such as Spring Break are accounted for in the calendar but do not alter the milestone structure. By adhering to this roadmap, we aim to deliver a fully functional, tested, and scalable app by early May 2026, with room for future enhancements like cloud synchronization and gamification.

Phase 1 (Weeks 1–5): Foundational Database Linking and Core Logic

This phase establishes the core data models, persistence layer, and baseline application logic required for directive generation and scheduling. Work in this phase focuses on building the foundational infrastructure upon which all future features depend.

  1. UI Components: Implement the Settings Page as the central access point for user customization. Create the Frequency Customization Screen to allow users to specify how often directives should be delivered. Implement navigation between the home, settings, and customization screens.

  2. App Logic Layer: Implement random category and directive selection functions, including duplicate avoidance. Create a directive scheduling function that assigns directives within the user's defined action window. Encapsulate logic in ViewModels and combine functions to implement automated directive delivery using WorkManager and Android's notification APIs, respecting action windows and frequency limits.

  3. Local Data Layer: Define and implement Room entities for directives, categories, active hours, and recent directives. Create a local datastore for user preferences. Implement DAOs to support CRUD operations and reactive data streams for UI.

  4. Key Deliverables: Functional settings and frequency configuration UI; working local database with linked entities; verified random selection and scheduling logic; directive response and history tracking.

Phase 2 (Weeks 6–10): Added Functionality and Feature Completion

This phase focuses on completing the core directive experience by implementing improvements to the delivery algorithm, notification interaction, and expanded user-accessible data management. The emphasis is enabling users to receive, respond to, review, and manage directives in a reliable and intuitive way.

  1. UI Components: Launch the Directive Response Screen when a notification is tapped, displaying options based on the user's selected interaction level. Enhance the home screen dashboard to show recently delivered directives, send times, and completion status. Add controls to delete history entries and manage custom directives. Finalize dark mode support and general UI polish.

  2. App Logic Layer: Improve notification scheduling to conserve battery and avoid repeated directives. Implement three engagement levels — No Engagement (notification only), Minimal Engagement (Yes/No confirmation), and Full Engagement (written response). Add logic for skipping, silencing, and postponing directives.

  3. Local Data Layer: Support deletion of recent directives from the response screen. Implement full CRUD for custom user-created directives stored under a "Personal" category. Expand the database with additional preloaded directives.

  4. Notification System: Tapping a notification opens the Directive Response Screen directly. Add in-notification response actions (completion confirmation or free response). Ensure notifications are cancellable, reschedulable, and postponeable, and validate reliability across device restarts and background states.

  5. Key Deliverables: Fully automated directive notification system with complex algorithm; functional directive response flow by engagement level; recent directive history management; support for custom directives; polished and accessible UI including dark mode.

Phase 3 (Weeks 11–15): Polishing, Stretch Goals, and Deployment Preparation

This phase serves as a refinement and expansion period focused on stability, client feedback, stretch goal implementation, and preparing the application for public testing and deployment. Core functionality is considered complete entering this phase.

  1. UI and UX Polish: Apply bug fixes and refinements based on internal testing and sponsor feedback. Improve navigation flow, animations, and visual consistency. Finalize the onboarding flow, including legal disclaimers, permission prompts, and an introduction tutorial screen.

  2. App Logic and Performance Optimization: Optimize scheduling and notification logic to reduce battery and CPU usage. Address edge cases with overlapping Action Windows and rapid preference changes. Improve error handling, logging, and fail-safe behaviors.

  3. Stretch Goals and Optional Features: Begin optional Firebase integration for community-shared directives. Explore cross-platform iOS implementation. Implement infrastructure hooks for future leaderboards, an admin dashboard, and premium directive packs. Complete active hours refactoring to support multiple action windows per day.

  4. Testing and Deployment: Conduct end-to-end testing across multiple Android versions and both physical and emulated devices. Perform usability testing against defined performance and learning metrics. Prepare Google Play Store assets (description, screenshots, privacy policy). Deploy to internal testing track for final validation.

  5. Key Deliverables: Stable, polished application meeting all performance and usability requirements; optional cloud feature prototypes if pursued; fully tested MVP ready for public or sponsor-facing release; Google Play Store deployment for testing or launch.

The milestone roadmap above outlines a phased development approach aligned with the system’s architecture, enabling parallel implementation while preserving critical dependencies. Phase 1 establishes the foundational data models, directive selection logic, scheduling mechanisms, and core settings UI that all subsequent features rely on. Phase 2 builds upon this foundation by completing the end to end directive experience, including interactive notifications, engagement level responses, directive history management, and user created content, with UI, logic, and database enhancements progressing concurrently. Phase 3 focuses on refinement, optimization, and scalability, incorporating bug fixes, performance tuning, usability improvements, optional cloud integration, and deployment preparation. Throughout development, the offline first requirement is preserved, cloud features remain isolated from core functionality, and testing is performed incrementally to ensure stability, reliability, and readiness for release.

This phased approach builds logically, addressing risks through mid-project safety integration and ensuring a robust foundation for post-MVP expansions.
